## Решения, уточняющие PDF

- **Основная платформа: Ext JS 7.7.0.31 (release 7.7.0), Classic.** Предположение PDF о production-target 7.9 не применяется. 7.9 остаётся референсом и отдельным необязательным этапом после 7.7; совместимость с ней не заявлять без отдельной сборки и проверок.
- **Обновить стандартные значки.** Пользователь явно запросил новый набор после чтения PDF. Правило PDF «v1 без собственных sprites» заменено: сначала зафиксировать Classic baseline, затем создать согласованный Nordic icon set с теми же геометрическими контрактами. Не объявлять эту работу выполненной, пока набор не создан и не проверен.
- **Геометрия 1:1, цель и выпускной критерий — отсутствие изменений.** Порог PDF ≤1 CSS px использовать только для диагностики. Любое ненулевое расхождение объяснить и исправить; не принимать его автоматически. Шрифтовые и box-model computed values должны совпадать.
- Скриншот Nordic обрезан справа, его масштаб/viewport неизвестны; это источник визуальных решений, не измерительный baseline. PDF на стр. 14 называет 1032×1211, прежние заметки содержат другое значение. Размеры исходных файлов измерить фактически, не растягивать один скриншот к другому ради PASS.
- Примеры кода PDF концептуальные. Не копировать синтаксис, переменные, manifest или CSS без проверки по SDK/Cmd. Глобальный ellipsis/nowrap и transform:none со стр. 16 не применять автоматически: это может менять поведение и скрывать проблемы.

## Архитектура

Отдельный Sencha Cmd package theme-nordic-blue, type=theme, toolkit=classic, extend=theme-classic. Сохранить сгенерированную .sencha/package. В установленном SDK classic/theme-classic/package.json содержит sencha.name=theme-classic, alternateName=ext-theme-classic. TestApp использует этот alias.

Начать с инспекции существующего workspace и TestApp; не создавать второй framework tree и не заменять приложение без необходимости. SDK ext-7.7.0.31 и TestApp/ext не редактировать. Приложение-потребитель переключает только выбранную тему; добавление theme-lab и build profiles допустимо в тестовой инфраструктуре и не должно требовать изменений production-компонентов.

Theme API и ограниченный allowlist конкретных color variables предпочтительны. Не менять глобальный $base-color. Tokens хранить в sass/var/all.scss, компонентные переменные — по Ext namespace. Проверять реальное место объявления и использование каждой переменной: даже существующая переменная может не влиять на нужный UI. Не копировать весь Sass Classic. Не создавать новые ui для замены default и не вводить JS overrides. Каталог overrides/ остаётся пустым.

Запрещено менять font-family/size/weight/line-height/letter-spacing/text-transform, padding/margin/spacing, width/height/min/max, border-width, box-sizing, frame padding/radius, trigger dimensions, icon boxes и позиции. Radius всех компонентов наследовать. Удаление градиента допускается после сравнения; новые тени отложить до прохождения геометрии, затем проверить clipping и overflow.

## Новый набор значков

Сначала построить каталог всех фактически используемых символов и их источников: PNG/GIF, sprites, glyph/font, CSS и overrides приложения. Обязательно покрыть panel/window tools, form triggers и spinner, grid sort/menu, button/menu/split arrows, tabs close/scroll, tree/expand/folder, date/calendar/month arrows, paging и editor toolbar. Проверить также checkbox/radio, slider thumbs и loading assets: для каждого явно указать replace или inherit с причиной. Не предполагать, что любой UI symbol — файл images.

Создать manifest с semantic ID, parent path, способом отрисовки, размерами изображения и display box, state cells, offsets, прозрачностью, форматами, заменой и местом использования. Сверить обе SDK-копии. Изменённые значки проектировать на исходной pixel grid в стиле Nordic; обеспечить hover/focus/pressed/disabled/checked/open/sorted состояния и читаемость на Nordic surfaces. Векторный master допустим; runtime-формат должен соответствовать подтверждённому pipeline SDK. Не подключать новый icon font с другими метриками и не заменять стрелки Unicode/CSS triangles.

Для замены image resources использовать тот же относительный путь и совместимый формат в resources/images, проверив фактическую сборку. Размер sprite sheet, grid и offsets сохранять. Меняется рисунок внутри соответствующей ячейки. Для font/CSS icons нужен отдельный проверенный способ замены без изменения DOM, box и interaction. Если это невозможно, оформить блокер конкретного значка, а не сдвигать его top/left/transform. Исходники, лицензии и сгенерированные assets хранить отдельно; не копировать весь Classic resources в тему. Наследовать все незаменённые ресурсы из текущего SDK. Создание нового набора разрешено пользователем; интеграция готового результата требует его отдельного явного одобрения, как описано ниже.

### Плотность пикселей без изменения размера

По возможности повысить чёткость на HiDPI: подготовить векторные masters и отдельные 1x/2x runtime-варианты (3x только при подтверждённой необходимости и поддержке pipeline). **Физический размер значков в интерфейсе не меняется:** при одинаковом масштабе страницы и DPR сохраняются CSS width/height, rect, hit area, отступы и положение. Например, 16×16 CSS px остаётся 16×16 CSS px; bitmap 32×32 используется как 2x-ресурс и не отображается размером 32×32 CSS px. Изменение DPI-метаданных файла или простое увеличение готового bitmap не создаёт новой детализации; экспортировать из master с достаточным качеством.

Исходный 1x-контракт Classic сохраняется. У альтернативного 2x sprite sheet число пикселей может удвоиться, но логические размеры sheet/cells, CSS background-size и state offsets должны соответствовать исходному контракту, а не увеличивать значок. Это уточняет прежнее требование одинаковых размеров изображений: неизменны отображаемые размеры и 1x fallback; плотные ресурсы могут содержать больше пикселей. Не добавлять background-size или переключение ресурсов вслепую: доказать совместимость с Cmd, фактическими sprites и поддерживаемыми браузерами в отдельном preview/fixture. Если безопасный HiDPI-вариант невозможен, сохранить качественный 1x, описать причину и показать пользователю. Не увеличивать размер элемента ради резкости.

Проверить DPR=1 и DPR=2 отдельно: Classic и Nordic сравнивать при одинаковом DPR/zoom. Rects, state offsets и hit areas должны совпасть в CSS px; в каждом окружении проверить отсутствие blur, clipping и захвата соседней ячейки спрайта. В manifest записать density, bitmap dimensions, CSS dimensions, логические offsets, способ выбора ресурса и fallback.

### Одобрение набора пользователем

После получения полного набора показать пользователю контактный лист всех значков и состояний, Classic→Nordic, preview в реальном размере и увеличенные фрагменты 1x/2x. Приложить редактируемые masters, runtime-кандидаты, список исключений и результаты проверки размеров. Перевести TASK-004 в **WAITING_USER_APPROVAL** и запросить явное одобрение конкретной версии набора. Отсутствие ответа не является одобрением.

До одобрения не интегрировать набор в рабочую тему (TASK-013), не утверждать его Nordic golden и не отмечать TASK-004 DONE. Технический preview для показа и проверки плотности разрешён. Независимые задачи можно продолжать. Зафиксировать решение пользователя, дату и hash/версию одобренного manifest; существенное изменение artwork, состояний или плотных вариантов после одобрения требует повторного показа изменённой части.

## Проверки и выпуск

Один детерминированный fixture и одинаковые данные/состояния для Classic и Nordic. Фиксировать OS, browser/version, fonts, viewport 1280×1600, DPR=1, locale/timezone, даты, animations/caret. Дождаться Ext-ready, загрузки данных/шрифтов и окончания layout; одного networkidle недостаточно. Матчить элементы по стабильным fixture IDs и semantic roles, не по индексу DOM или динамическим Ext IDs. Проверять полноту покрытия: пустые выборки и отсутствие ожидаемых элементов — FAIL.

Снять DOM rects и typography/box-model, проверить каждое состояние и действия клавиатурой/мышью. Три визуальных слоя: geometry; структурное сравнение с нейтрализацией цветов; собственные Nordic golden snapshots. Из-за нового icon set Classic↔Nordic pixel-diff будет отличаться и после нормализации: учитывать только перечисленные icon regions, проверять их geometry отдельно, проверять новый набор по Nordic golden. Не маскировать целиком triggers/tools или соседний текст. Сохранять raw/normalized/diff и отчёт, а не только PASS.

Числа PDF threshold=0.1, maxDiffPixelRatio=0.001 — стартовые предложения, не доказательство совместимости. Подобрать на стабильном окружении и отрицательных контрольных изменениях. Изменение golden не должно автоматически принимать регрессии.

Проверить development/testing/production application builds, sprites/resources и загрузку без 404, console errors. Отдельный package build нужен при обещании standalone package; при включении исходников темы в Cmd app он не обязателен сам по себе. Сборки разных SDK никогда не смешивать. Не объявлять тему готовой до проверок на собранном приложении; отчёт должен содержать команды, версии, результаты и ограничения.

## Как выполнять карточку

Брать только TODO с выполненными зависимостями. Прочитать исходники и текущее состояние, отметить IN_PROGRESS. Выполнить подзадачи, собрать указанные артефакты и доказательства, обновить карточку и индекс. WAITING_USER_APPROVAL означает ожидание явного одобрения набора значков; зависимая интеграция в это время не выполняется. DONE означает все критерии пройдены; план, созданный файл или старый build не являются доказательством. BLOCKED должен содержать конкретную причину, воспроизведение и необходимые данные. Не начинать реализацию темы в рамках подготовки этих инструкций.
